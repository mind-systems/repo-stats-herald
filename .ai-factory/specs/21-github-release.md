# 11.3 — GitHub release + version header

**Phase:** 11 — GitHub releases & versioning. Depends on 11.1 (version, `role_for_branch`/`BranchRole`), 11.2 (the note builder), 12.1 (a mapped app's declared languages, when one exists), Phase 3 (`GitHubAppAuth`), Phase 9 (Telegram delivery). Closes the phase: the version and note reach the release channels.

## Current state

After 11.1–11.2 Herald can build per-language notes for a staging/release push, but nothing resolves *which* languages are required, cuts a GitHub release, or adds the version header to the Telegram message. Phase 9's `DeliveryService` is transport-only (no per-push send); reports fire it on a cadence. The GitHub-release channel does not exist yet, and nothing resolves the required-language union or heads the Telegram message with a version. Both the Telegram and GitHub-release languages are configured defaults (RU, EN respectively, per `docs/behavior/delivery.md`), not literals to be hardcoded here.

## Change

Resolve the required-language union once, build the notes once, then publish the GitHub release and head the Telegram message — each from its own language in the same result.

- Extend `DeliveryPlan` (9.1/9.3) with `github_release_language: str` (default `"en"`), mirroring the existing `language` field (Telegram, default `"ru"`) — both configured, never literals.
- On a `staging`/`release` push with a version (11.1 ≠ `None`): resolve the **required-language union** — `{plan.language, plan.github_release_language}` plus, when `plan.changelog_base_url` is set (resolved by 12.1), that app's declared languages via `ChangelogClient.config(plan.changelog_base_url)` (12.1). **`config` is failure-isolated**: if it raises (app unreachable), the app is dropped from this delivery — the union stays the fixed-channel languages, and the changelog channel is skipped (12.2), while the GitHub release and Telegram still fire. The union, the app's declared languages (or their absence), and the built `notes` are **local values inside the single staging/release handler in `src/ingestion/router.py`** — not a returned/passed cross-module type; 12.2 extends the same handler scope rather than consuming a dedicated marker object.
- `Localizer.report_notes(release_report(repo, org_id, branch), repo, org_id, union)` (11.2.2 + 10.3) **once** — one resolution and one set of notes feeding every release channel.
- `src/delivery/github_release.py` — `GitHubReleaseClient.create(owner: str, repo: str, version: Version, body: str, prerelease: bool, target_commitish: str) -> str`: with the installation token from `GitHubAppAuth.token(org_id)` (Phase 3), `POST https://api.github.com/repos/{owner}/{repo}/releases` (`tag_name` = `str(version)`, the canonical `Version.__str__` render, 11.1 — no independent formatting; `target_commitish` = the push's `after` SHA, so a staging pre-release tags the pushed commit rather than whatever the mirror's default-branch HEAD happens to be; `body` = `notes[plan.github_release_language]`; `prerelease` = `True` for `BranchRole.STAGING`, `False` for `BranchRole.RELEASE`, both via `role_for_branch` (9.1) — never a `branch == "staging"` string compare). Returns the created release's `html_url` from the Releases API response — the `github_url` 12.2's changelog `entry` needs; nothing captured it before this. `owner` = `event.org_login` (already on `PushEvent`, `src/ingestion/models.py:17`) — Herald's App installs are org-scoped, so the pushing org's login is the repo owner; no new field on `PushEvent`/the webhook contract. `httpx`, `base_url="https://api.github.com"`, headers `Authorization: Bearer <installation token>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28` — mirroring `GitHubAppAuth`'s own request shape (`src/github/app_auth.py:65-70`), token minted per-org via the installation-token path (not the App JWT). Non-2xx raises. Tag creation is implicit in the release call (`contents: write`).
- Extend `DeliveryService` (9.3): for a `staging`/`release` push, prepend the version header (`v1.2.0-rc` / `v1.2.0`, `str(version)`) to `notes[plan.language]` (the Telegram message).
- **The whole staging/release delivery fan-out runs as a single isolated background task**, following `src/ingestion/router.py`'s existing precedent (`background_tasks.add_task(_run_isolated, "<label>", <delivery_fn>, event)`, the same pattern already used for `knowledge_sync.on_push`/`episodic_writer.write`) — so the webhook responds promptly instead of blocking on sequential network calls (GitHub Releases → Telegram → the changelog app, 12.2), which a slow/timed-out response would turn into a GitHub redelivery and a duplicate release/entry. Inside that one task, in order: **`mirror.ensure(repo, org_id)`** (the composition-root `RepoMirror`, `src/main.py`'s lifespan, reachable via app state — the same instance the rest of the app uses) → **compute the version** (11.1's `Versioner`; a `None` version ends the task here) → resolve the union → `report_notes` once → create the release (capture `github_url = create(...)`) → deliver the version-headed Telegram → (12.2) the changelog `entry`. A `ChangelogClient.config` failure during union resolution, and the changelog `entry` call itself (12.2), are each individually caught and logged so the release and Telegram still fire even when the app leg fails.
- Wire into ingestion: register the one background task on a `staging`/`release` push; inside it, `mirror.ensure(repo, org_id)` → compute the version (11.1) → resolve the union → build the notes once (`report_notes`, 11.2.2 + 10.3) → create the release (`owner=event.org_login`, `notes[plan.github_release_language]`, `target_commitish=event.after`, capturing `github_url`) → deliver the version-headed Telegram (`notes[plan.language]`) → (12.2) the changelog entry.

## Guards

- **One `report_notes` call per push** — feeds every release channel; no per-channel re-resolution.
- Channel languages come from the delivery plan / config (`plan.language`, `plan.github_release_language`) — never literals in this task's code.
- The release is created once per version; a `None` version (11.1 back-merge/skip) cuts nothing.
- Branch role compared in **one place** — `role_for_branch` (9.1): `BranchRole.STAGING` → pre-release, `BranchRole.RELEASE` → full release; never an inline `branch == "staging"` compare in this task.
- `target_commitish` is always the push's `after` SHA — never left to default to the mirror's default-branch HEAD, which would mistag a staging pre-release.
- Release creation via the installation token (`GitHubAppAuth.token(org_id)`); API errors raise; requests carry `X-GitHub-Api-Version: 2022-11-28`.
- **The whole fan-out is one isolated background task** (`background_tasks.add_task(_run_isolated, ...)`, mirroring `knowledge_sync.on_push`/`episodic_writer.write` in `src/ingestion/router.py`) — the webhook response never blocks on the GitHub/Telegram/changelog network calls; `create`'s returned `html_url` is captured in that task's locals and threaded to 12.2's `entry` call, never re-fetched.
- **The fan-out owns `mirror.ensure(repo, org_id)`, run as the task's first step**, before computing the version (11.1's `Versioner` reads the mirror) and before building the release report (`SinceDeployWindow`/`SummarySection` read the mirror, 11.2.1/10.1.2) — never relying on another background task (`knowledge_sync.on_push`) having ensured it first. Background-task ordering is not a contract, and `knowledge_sync` may be absent (`getattr(request.app.state, "knowledge_sync", None)`, `src/ingestion/router.py`). This satisfies 50's caller-side ensure precondition for the release path.
- **Mandatory test over mocked `report_notes`/`GitHubReleaseClient.create`/`DeliveryService.deliver`:** exactly one `report_notes` call per push, feeding both the release body and the Telegram header from its result; the union passed to it equals `{plan.language, plan.github_release_language}` ∪ the mapped app's declared languages (when one exists); a `None` version → `report_notes`/`create` not called and the Telegram send carries no version header.
- **An unreachable app never blocks the other channels** (ROADMAP Phase-12 invariant) — a `ChangelogClient.config` failure during union resolution is caught, degrades the union to the fixed-channel languages, and marks the changelog channel unavailable; the release and Telegram are unaffected. Mandatory test (mocked `ChangelogClient.config` raising): the release is cut and the version-headed Telegram delivered; the union passed to `report_notes` is exactly `{plan.language, plan.github_release_language}`; the changelog channel is marked unavailable.

## Verification

- A `staging` push → a GitHub pre-release tagged `v1.2.0-rc` with the body in `plan.github_release_language`, plus a Telegram message headed `v1.2.0-rc` with the note in `plan.language` — both drawn from one `report_notes` call.
- A repo mapped to a changelog app declaring a third language → that language is present in the same `notes` result, at no extra resolution cost.
- A default-branch push → a full GitHub release `v1.2.0`.
- A back-merge (11.1 → `None`) → no release, and the Telegram message carries no version header.
- A mapped repo whose app is unreachable at `config` time → GitHub release + Telegram still delivered; union = the fixed-channel languages; changelog skipped, no crash.
- The release request targets `POST https://api.github.com/repos/{event.org_login}/{event.repo}/releases` with `target_commitish=event.after` — a staging push tags the pushed commit, not the mirror's current default-branch tip.
