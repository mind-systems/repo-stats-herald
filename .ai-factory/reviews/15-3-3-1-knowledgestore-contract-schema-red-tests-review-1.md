# Code Review — 3.3.1 KnowledgeStore contract + schema (red tests)

**Scope reviewed:** `src/core/db.py`, `src/knowledge/schema.sql`, `src/knowledge/store.py`, `tests/knowledge/conftest.py`, `tests/knowledge/test_knowledge_store_contract.py`, `pyproject.toml`, `CLAUDE.md`, `uv.lock`.

**Verdict:** No correctness, security, or contract bugs. The scaffold does exactly what the task requires: an asyncpg pool factory with a `vector` codec, the `chunks` DDL, the `KnowledgeStore` ABC with a raising `PgVectorStore` stub, and three red contract tests that fail at the stub (not at import/fixture) on a dev pgvector. Below are non-blocking observations only.

## What was verified

- **Red-for-the-right-reason.** All three tests call `await store.upsert(...)` (or `delete`/`query`) as their first store interaction; the stub raises `NotImplementedError`, so each is red at the stub rather than at an assertion or a collection error. `pytest --collect-only` collects all 11 tests (3 new async + 8 existing sync) with no errors — `asyncio_mode = "auto"` recognizes the async tests and leaves the existing sync suites (`ingestion`, `github`) untouched.
- **Cosine ordering pin is sound and adversarial.** Query vector = unit axis 0. `nearest` (axis0, +1) → cosine distance 0; `middle` (axis1, +1) → orthogonal, distance 1; `farthest` (axis0, −1) → opposite, distance 2. The test asserts the exact index order `[nearest, middle, farthest]`, so a reversed `ORDER BY` in 3.3.2 (farthest-first) would fail — the planted-farthest hazard the spec names is genuinely caught, not a "returns some rows" pass.
- **Atomic-replace pin is correct.** Upsert 5 then upsert 2; asserts `chunk_index` set is exactly `[0, 1]`. A naïve append/`ON CONFLICT DO UPDATE` leaves stale indices `2..4` (→ `[0,1,2,3,4]`, fails) and a plain re-INSERT of indices 0,1 hits the PK and raises (fails) — only a delete-then-insert replace passes. The PK `(repo, path, chunk_index)` structurally forbids duplicate indices, as intended.
- **Scoped-delete pin is correct.** Seeds `(repo, a)`, `(repo, b)`, `(other_repo, a)`; deletes `(repo, a)`; asserts the survivors are exactly `{(repo, b), (other_repo, a)}` — it verifies both the same-repo sibling path and a same-path different-repo row are spared, so a delete that keyed on `path` alone would fail.
- **Schema.** `vector(768)` matches `nomic-embed-text` (`Settings.embed_model`, 3.2); PK and `hnsw … vector_cosine_ops` cosine index match the spec. DDL is idempotent (`IF NOT EXISTS` throughout) and executes as one multi-statement string via asyncpg's simple-query protocol (no args passed to `conn.execute`), which is valid.
- **Codec round-trip.** `_encode_vector`/`_decode_vector` produce/parse pgvector's `[a,b,c]` text form correctly. Not exercised on the red path (query stub raises before decode); it becomes live in 3.3.2.
- **Deps/lock.** `asyncpg` (0.31.0) is a runtime dep, `pytest-asyncio` (1.4.0) a dev dep, both present in `uv.lock`; `asyncio_mode = "auto"` added without disturbing `testpaths`/`pythonpath`. CLAUDE.md's module table updated for `create_pool` and `src/knowledge/`.

## Non-blocking observations

1. **Pool-init codec registration assumes the `vector` type already exists — `schema.sql`'s `CREATE EXTENSION` cannot cover a fresh DB via the pool path.** `asyncpg.create_pool` defaults to `min_size=10`, so the `init=_init_connection` callback runs `conn.set_type_codec("vector", schema="public", …)` on connections opened *during* `create_pool()` — before the `pg_pool` fixture applies `schema.sql`. asyncpg resolves the `vector` type OID at codec-registration time, so against a database where the extension is not yet installed, `create_pool` raises "unknown type: public.vector" and the `CREATE EXTENSION IF NOT EXISTS vector` in `schema.sql` never gets a chance to run. On the intended dev machine the extension is a documented per-machine prerequisite (`CLAUDE.md` first-time setup; spec 06 guard "assumes the `vector` extension exists"), so this is within contract and the tests are red at the stub as required. It only bites a bare/CI Postgres without pgvector, where the failure would surface as a fixture error rather than the stub error. Worth a note for whoever wires CI: provision pgvector (or install the extension) before this suite runs. No code change needed for the documented environment.

2. **Minor duplication.** `EMBEDDING_DIM` and the unit-vector builder exist in both `tests/knowledge/conftest.py` (`make_chunk`) and `test_knowledge_store_contract.py` (`_unit_vector`). Harmless; the query vector legitimately isn't a `Chunk`, so a small local helper is reasonable. Could later fold the dim constant into one place.

3. **Default pool sizing in tests.** `create_pool` uses asyncpg's default `min_size=max_size=10`, so each `pg_pool` fixture opens 10 connections per test. Functionally fine and fast against local Postgres; a `min_size=1` for the test factory would be lighter, but it's not a correctness issue and `create_pool` is production infra, not test-only.

REVIEW_PASS
