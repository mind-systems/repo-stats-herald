## Deferred observations (non-blocking — no action required for 10.2)

1. **`PerBranchSection`'s time window is a *superset/approximation* of the schedule window, by design of the section contract.** `Report.build` hands every section the same `(before, after)` SHAs; `active_branches` (by its own docstring) derives the window from *those commits' dates*. `TimeWindow` picks `before = commit_at_or_before(now - delta)`, whose date is ≤ `now - delta` and can be much earlier when the canonical ref has a commit gap around the boundary. Consequence: on a repo with such a gap, the per-branch section can surface *non-canonical* branch commits that fall between the `before` commit's date and `now - delta` — i.e. slightly older than the intended daily/weekly window. Symmetrically, unmerged feature-branch commits *newer* than the canonical tip are excluded (the documented "anchored on the canonical ref" tradeoff). `SummarySection`/`RemainingSection` are exact; only the per-branch enumeration is affected, and only in these boundary/gap cases. This is inherent to sections receiving SHAs (not a timestamp) — no real commit sits exactly at `now - delta`. Recorded for 10.3/future tuning; not a defect in this change.

2. **`scripts/report.py` hard-requires the GitHub-App settings** (`github_app_private_key_path`, `github_app_id`) — it reads the PEM unconditionally, unlike `main.py`'s gated assembly. This matches the existing `scripts/backfill.py` pattern (a report run needs the mirror), and in production those settings are always present, so the cron is fine. Noted only so a misconfigured environment fails loudly at startup rather than silently.

3. **`.env.example` ships a populated `REPORT_SCHEDULES` value** (vs. the blank convention of other multi-value vars). `.env.example` is documentation only (Settings loads `.env`), and a concrete example is genuinely useful here, so this is intentional and harmless.
