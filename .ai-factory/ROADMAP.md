# Project Roadmap

> A press secretary that understands each project in an organization, tracks how its features progress and interconnect, and narrates that in human language — driven by GitHub pushes, delivered by branch.

## Active tasks

> `---STOP---` is a barrier the orchestrator never crosses: it processes only the tasks above the first one. ### Phase 19 — Boundary representation mismatches

Three defects with one shape: a value is represented differently on the far side of a boundary than Python assumes on this side. `TelegramClient` builds `https://api.telegram.org/bot<token>/sendMessage` and calls `raise_for_status()`, whose exception text carries that URL, so any caller logging a delivery failure writes the bot token into the log. `Settings.postgres_dsn` interpolates user and password into a URL with no percent-encoding, so a password holding any URL-reserved character yields a DSN that addresses the wrong host or fails to parse — and this is the production path through `create_pool`. Telegram counts its 4096-character message limit in UTF-16 code units while the chunker counts Python code points, so a message dense in astral-plane characters produces a part the Bot API rejects. Pinned: [delivery](../docs/behavior/delivery.md) states no rule about the message boundary today — the governing spec states the counting rule first and the chunker is brought to it, never the reverse; the token never reaches an exception string; the DSN is composed by a URL builder rather than by interpolation.

- [ ] **19.1 — Scrub the bot token from delivery failure paths** — `TelegramClient.send` (`src/delivery/telegram.py`) builds `https://api.telegram.org/bot{token}/sendMessage` and calls `raise_for_status()`; the resulting `httpx.HTTPStatusError` carries that URL in its string form, and every `httpx.RequestError` exposes `.request.url`, so any caller logging a delivery failure — or the request object reachable from it — writes the bot token into the log. Let no token-bearing exception escape `send`: raise a client-owned error holding no credential in its message or its attributes, covering both the non-2xx and the transport-failure path. Guard: `send` still raises on both, so 9.2's signalling discipline is unchanged; the status and a redacted endpoint stay available for diagnosis. Spec: `.ai-factory/specs/56-telegram-token-redaction.md`.
- [ ] **19.2 — Percent-encode credentials in `postgres_dsn`** — `Settings.postgres_dsn` (`src/core/config.py`) interpolates `postgres_user`/`postgres_password` into a URL with no encoding, and this is the production path `src/main.py` hands to `create_pool`, so a password holding `@`, `:`, `/`, `#`, or `?` yields a DSN that addresses the wrong host or fails to parse. Percent-encode both credential components. Guard: credentials with no reserved character produce a byte-identical DSN to today's, so no existing environment changes behavior; the same unescaped helper is mirrored in `tests/episodic/conftest.py`, `tests/graph/conftest.py`, and `tests/knowledge/conftest.py` and all three move with it — one concern, not separate tasks. Spec: `.ai-factory/specs/57-postgres-dsn-encoding.md`.
- [ ] **19.4 — Chunk Telegram messages by UTF-16 code units** — `TelegramClient._chunks` (`src/delivery/telegram.py`) compares `len(text)` against `TELEGRAM_MESSAGE_LIMIT` and slices by the same code-point index, but Telegram counts UTF-16 code units where every astral-plane character costs two, so a message dense in them passes the local check and is rejected by the Bot API. Measure and split by UTF-16 code-unit count per 19.3's pinned rule. Guard: an all-BMP message chunks exactly as today; parts still rejoin to the original with no loss, duplication, or reordering; no split falls between the halves of a surrogate pair; sending stays plain text, so no formatting entity is at risk. Depends on 19.3. Spec: `.ai-factory/specs/59-utf16-message-chunking.md`.

### Phase 20 — Thin the ingestion router

[ARCHITECTURE.md](ARCHITECTURE.md) names "logic in entry points" an anti-pattern and pins that routers stay thin while services own business logic. `_deliver_release` is roughly eighty-five lines of release fan-out — version resolution, note generation, GitHub release, Telegram, changelog entry — sitting inside `src/ingestion/router.py`, a module whose job is receiving and verifying webhooks. It is the only deferred observation across the whole history naming a direct architecture violation, and it grew across 11.3 and 12.2 rather than arriving at once. This phase moves the fan-out behind a delivery-side service the router calls, leaving the router with receive, verify, parse, dispatch. Decided in the same pass: `RepoMirror`'s git calls are blocking `subprocess.run` invoked from an async background task, so either the mirror gains an async boundary or the background work moves off the event loop. Pinned: no behavior change — the same channels fire in the same order, with the same isolation and the same failure containment.

- [ ] **20.1 — Extract the release fan-out into `ReleaseDelivery`** — `_deliver_release` (`src/ingestion/router.py`) is roughly eighty-five lines orchestrating the whole staging/release fan-out — mirror ensure, version resolution, the changelog-app language union, release-note localization, GitHub release, Telegram, changelog entry — inside the webhook router, taking eight untyped collaborators as keyword arguments and bypassing the constructor injection this project pins. Both the GitHub-release and changelog-wiring task specs named `src/delivery/service.py` as the file to edit; the logic grew in the router instead. Move it into a `ReleaseDelivery` class in `src/delivery/service.py`, collaborators typed and injected at construction, one method the router awaits. Guard: no behavior change — same legs, same order, same graceful degradation, same isolation, same log lines; the changelog base URL is read as a plain attribute rather than through a defensive lookup whose fallback is unreachable. Spec: `.ai-factory/specs/60-release-delivery-extraction.md`.
- [ ] **20.2.1 — Concurrency contract for the async mirror (red scenarios)** — `RepoMirror`'s own spec guards that it "introduces no new concurrency surface beyond what 3.1.1 already pinned", but making its git methods awaitable adds yield points inside methods that today run start to finish with none, so interleavings that are structurally unreachable become reachable. Re-pin the surface before the conversion: two overlapping `ensure` calls for a never-cloned repo must not both take the clone branch; the finished-worktree bookkeeping must stay consistent under genuine thread concurrency; `git worktree prune` must not race a worktree being created; and 3.1.1's torn-tree isolation must still hold when `ensure` and `tree` for one repo overlap. Guard: no production code and no synchronization mechanism chosen — that is 20.2.2's call against these invariants; `GitHubAppAuth`'s per-org `threading.Lock` already covers double-minting and is not re-litigated. A `git fetch` or first `clone` therefore stalls the loop for every concurrent request. ### Phase 16 — Historical replay (backtest)

Blocked on the whole broadcast slice — episodic backfill and code-derivation (Phases 4–5), the reasoner (7), narration (8), Telegram delivery (9), the reporting engine (10), and versioning windows (11) — and deliberately sits last: replay orchestrates finished parts instead of threading a new concern through their tasks. Today a repo Herald starts serving gets its past *indexed* (4.4) but never *narrated* — no one can open the channel and read how the project grew. Replay drives the derivation engine over the repo's history in simulated time — semantic memory tracks the replay cursor, not `HEAD` — cutting a report every N active (non-empty) days and a release-style note at each historical version tag, delivered with historical dates to a Telegram channel designated at launch; the channel becomes the project's chronicle, and the run doubles as end-to-end acceptance of both narration types over a real history. Pinned: memory writes idempotent across re-runs while narration regenerates fresh (texts are a projection of memory, not part of it); runs boundable (K windows / stop at a commit) for small-dose checks; N is a launch parameter (15 ≈ sprint, 30 ≈ monthly); no outward effect beyond Telegram — no tags, GitHub releases, or changelog writes. Behavioral contract: [replay](../docs/behavior/replay.md).

### Phase 17 — Reasoner-driven version increment

Blocked on Phase 11 (versioning) and Phase 7 (the reasoner). Today the increment component is a fixed configuration value (`version_increment`, Phase 11): every bump advances the same part — patch by default — whether the change is a breaking rewrite, a feature, or a one-line fix. This phase turns the increment into a **policy seam**: the reasoner (Phase 7), which already understands a project's changes semantically, judges the significance of the change set since the last version and picks `major`/`minor`/`patch`. Pinned: precedence is manual override → reasoner judgment → the configured default component, and the reasoner-driven policy **degrades to that configured default** whenever the reasoner is unavailable or unsure, so a release is never blocked. The judgment runs once at assignment and its result is recorded as the git tag, so the version stays reproducible after the fact even though the judgment itself is non-deterministic — the departure from Phase 11's pure git-derivation is deliberate and bounded to assignment time. Concept: [reasoner-driven version increment](../docs/concepts/version-increment-policy.md).
