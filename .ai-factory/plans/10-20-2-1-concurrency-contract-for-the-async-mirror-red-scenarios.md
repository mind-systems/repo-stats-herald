## Background (read before implementing)

Ground truth for this task:
- `src/github/mirror.py` — `RepoMirror`. Note that every shelling-out method funnels through the injectable `run` callable (`__init__`'s `run=subprocess.run`), and `_run_git`. The two invariants the spec calls "resting on the no-yield accident today":
  - `ensure` (lines ~108–131): `if not bare_path.exists(): clone --mirror else fetch`, then `_reclaim_finished_worktrees`, then `git worktree prune`. **The check-then-clone has no lock.**
  - `tree` (lines ~133–163) registers a finished worktree in `self._finished_worktrees` under `self._finished_worktrees_lock` in its `finally`; `_reclaim_finished_worktrees` (lines ~165–182) snapshots+clears the list **under the same lock**, then runs `git worktree remove` outside it. `sweep_worktrees` also runs `git worktree prune` per bare repo.
- `tests/github/conftest.py` — provides the `mirror`, `local_upstream`, `auth` fixtures and the `_git`/`_commit` helpers. The `mirror` fixture clones from a plain filesystem path (no token minting) and does **not** pass a custom `run`.
- `tests/github/test_mirror_isolation.py` — the existing concurrency module (2 threaded isolation tests, 3.1.1's torn-tree contract). Its header docstring still describes the pre-implementation stub era and is now stale.
- `tests/github/test_mirror_lifecycle.py`, `tests/github/test_mirror_credentials.py` — the single-threaded lifecycle group and the credential group; used only as pattern references (`_RecordingRunner` in the credentials module shows the injectable-`run` idiom).

Per the spec's guards: **no file under `src/` changes**, and **no synchronization mechanism is chosen** — the scenarios assert invariants; picking a lock/serialization to satisfy them is 20.2.2's job. `GitHubAppAuth`'s per-org `threading.Lock` (double-minting) is out of scope and not re-pinned.

Each scenario must, per the spec, **state which of two it is**: red against today's synchronous mirror when driven with real threads, or inapplicable against it for a stated reason — and either way express the invariant the async conversion must satisfy. Expected classifications are given per task; the implementer must assert the invariant and record the *observed* status with its reason in the test's own docstring, rather than assume.

## Tasks

### Phase 1: The controlled-subprocess harness

- [x] **Task 1: Add a `GatedRunner` interleaving harness to conftest**
  Files: `tests/github/conftest.py`
  Add a `GatedRunner` class (and a small helper to build a `RepoMirror` wired to it, in the style of the inline mirror construction already used across the mirror suites) that wraps real `subprocess.run` so tests can force deterministic interleavings over genuine git subprocesses — this is the spec's "controlled git subprocess". Requirements:
  - It calls through to real `subprocess.run` (git actually executes against `local_upstream`), so worktrees, refs, and content are real; it only controls *when* selected commands run.
  - It records every dispatched git subcommand (the argv), so a scenario can assert e.g. how many times `clone` was dispatched. Follow the recording shape of `_RecordingRunner` in `test_mirror_credentials.py`.
  - It exposes a way for a test to register a gate keyed on a git subcommand (match on the second argv element, e.g. `"clone"`, or on a `("worktree", "add")` / `("worktree", "prune")` pair): when a thread is about to execute a gated command, the runner signals a `threading.Event` that the command was reached, and blocks on a caller-supplied `threading.Event`/`threading.Barrier` before executing. Use only `threading` primitives (`Event`, `Barrier`) — no `sleep`-based timing, so the interleaving is deterministic, not racy.
  - Gates must be per-subcommand so a scenario can hold thread A on one command while thread B proceeds on another.
  Keep it a test-only helper; it must not import from or modify `src/`.
  Also refresh `conftest.py`'s stale header docstring in the same edit: it still reads that the tests "are red against the `RepoMirror`/`GitHubAppAuth` stubs and must fail because the mirror/auth logic is absent" — the mirror logic now exists, so that statement is false. Replace it with an accurate description of what the fixtures and the `GatedRunner` provide.

### Phase 2: The four pinned scenarios

Add all four to `tests/github/test_mirror_isolation.py`. Refresh that module's stale header docstring (Task 6) as part of the same edit set. Each scenario uses real `ThreadPoolExecutor`/`Thread` workers and the `GatedRunner` from Task 1.

- [x] **Task 2: Scenario — two overlapping `ensure` calls never both take the clone branch** (depends on Task 1)
  Files: `tests/github/test_mirror_isolation.py`
  Two threads call `ensure(REPO, ORG_ID)` for a repo with no bare clone yet. Gate the `clone` command with a `threading.Barrier(2)` so both threads execute their clone only after both have passed `ensure`'s `bare_path.exists()` check (the check precedes `_run_git("clone", …)`, so arriving at the gated clone proves each saw `exists() == False`). Assert the invariant that **only one clone is dispatched** (e.g. `runner` recorded `clone` exactly once) — i.e. the two calls do not both take the clone branch.
  Handle the losing thread's failure explicitly: when both take the clone branch, the first `git clone --mirror` succeeds and the second raises `subprocess.CalledProcessError` (destination now non-empty; `_run_git` uses `check=True`). The worker must swallow/collect that expected `CalledProcessError` rather than let it propagate — the invariant lives in the shared `GatedRunner`'s recorded `clone` dispatch count (`count == 1`), evaluated after both threads join, not in whether a worker raised.
  This scenario is **explicitly red-only, and its forcing harness — not just its assertion — is revisited by 20.2.2.** A `Barrier(2)` on `clone` releases only once *two* threads reach the gated clone, which is precisely what forces the deterministic red today (no lock around check-then-clone → both pass `exists() == False` → both reach the gate → both clone). But once 20.2.2 serializes the check-then-branch, only one thread reaches `clone`; the other sees `exists() == True` and takes `fetch`, never arriving at the gate, so a two-party barrier would block the cloning thread forever (a hard deadlock if 20.2.2 holds a per-repo lock across the clone). A mechanism that deterministically forces both threads to clone can only do so while the bug is present — it is structurally red-only. Do **not** promise this test "turns green unchanged": the invariant that survives the conversion is `clone dispatched once`, and 20.2.2 must *relax the gate itself* (e.g. to a one-sided hold with a broken-barrier/abort path) when it makes the invariant hold. Record this in the test docstring — that the forcing harness, not only the assertion, is expected to change at conversion time.
  Expected classification: **RED against today's synchronous mirror under real threads** — the check-then-clone in `ensure` has no lock, so both threads take the clone branch (clone dispatched twice). This invariant rests only on today's no-interleave execution, not on any guard. Document this status and reason in the test docstring.

- [x] **Task 3: Scenario — finished-worktree bookkeeping stays consistent under genuine thread concurrency** (depends on Task 1)
  Files: `tests/github/test_mirror_isolation.py`
  Prime the mirror (`ensure`, then open and close one `tree` so a finished worktree is registered in `_finished_worktrees`). Then run, on real threads, a `tree` open/close (which appends under `_finished_worktrees_lock` in its `finally`) *concurrently* with an `ensure` (whose `_reclaim_finished_worktrees` snapshots+clears the list under the same lock). Note the harness limit: both critical sections are pure-Python and hold the *same* lock, with no git subprocess inside either lock-held section, so the `GatedRunner` (which only controls subprocess timing) cannot force the append and the snapshot-clear to interleave — and the lock precludes any true overlap by design, which is exactly the invariant. Use the `GatedRunner` only to run the two threads concurrently *around* those sections (e.g. gate `tree`'s `worktree add` against `ensure`'s `fetch`); lock-arbitration order is then non-deterministic. Assert pure consistency under **either** arbitration order: **no finished worktree is dropped from tracking without being removed, and none is removed twice or removed while still open** — every scratch is either gone from disk *and* absent from the list, or still tracked for the next `ensure`. Do not assert a specific ordering.
  Expected classification: **INAPPLICABLE against today's synchronous mirror — passes under real threads because `_finished_worktrees_lock` already serializes the append and the snapshot-clear.** This invariant rests on the existing lock, so genuine thread concurrency does not break it today; the scenario pins it so 20.2.2 must preserve an equivalent guarantee (a `threading.Lock` no longer serializes coroutines interleaving on one event-loop thread). Document this status and reason in the test docstring.

- [x] **Task 4: Scenario — `git worktree prune` must not race a worktree being created** (depends on Task 1)
  Files: `tests/github/test_mirror_isolation.py`
  Prime the mirror with a first `ensure(REPO, ORG_ID)` so the bare clone exists before either thread starts — the overlap being pinned is between a *second* `ensure` reaching `git worktree prune` and a `tree`'s `git worktree add`, never between the cloning `ensure` and a `tree`, since a `tree` cannot open until that clone has finished. On real threads, force an `ensure`'s `git worktree prune` (line ~131) to overlap a `tree`'s `git worktree add --detach` for the same repo, using the `GatedRunner` to release the `prune` and the `add` concurrently (gate one on reaching the other). Assert the created worktree survives: its directory exists, it appears in `git worktree list --porcelain`, and it yields exact ref content (`marker.txt`).
  Expected classification: the dangerous window is **internal to a single `git worktree add` subprocess** and cannot be forced open from outside, and today's synchronous mirror never overlaps `ensure`'s prune with `tree`'s add for one repo — so the observed status is expected to be **INAPPLICABLE** (the forced overlap does not reap the worktree). If the forced overlap does reap or corrupt the worktree, it is **RED** and a genuine race the conversion must guard. The implementer must run it and record the observed status with its reason in the docstring — do not assert green silently.

- [x] **Task 5: Scenario — 3.1.1's torn-tree isolation holds when `ensure` and `tree` for one repo overlap** (depends on Task 1)
  Files: `tests/github/test_mirror_isolation.py`
  Prime the mirror with a first `ensure(REPO, ORG_ID)` so the bare clone exists before the `tree` is opened — `tree` runs `git worktree add --detach` with the bare path as its working directory and cannot open against an object store that does not exist yet. Open a `tree(REPO, ORG_ID, ref_a)` and, while it is held open on one thread, run `ensure(REPO, ORG_ID)` on another (its `fetch --prune`, `_reclaim_finished_worktrees`, and `git worktree prune` all run against the same bare store), forcing the overlap with the `GatedRunner`. Assert the open tree is never disturbed: its path still exists, is not shared with any other checkout, and still reads the exact `ref_a` content (`content-a`) both during and after the overlapping `ensure` — extending 3.1.1's "concurrent trees stay isolated" contract to the `ensure`×`tree` overlap.
  Expected classification: expected **INAPPLICABLE against today's synchronous mirror** — `ensure` reclaims only worktrees already registered as finished (an open `tree` has not registered yet), `git worktree prune` skips a live directory, and a detached checkout does not move when `fetch` updates branch refs, so isolation holds; today the two also never overlap. The scenario pins the invariant across the conversion. The implementer must run it and record the observed status (RED if the overlapping `ensure` disturbs the open tree) with its reason in the docstring.
