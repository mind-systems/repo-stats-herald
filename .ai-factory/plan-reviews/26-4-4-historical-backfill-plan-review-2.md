### Critical Issues

**1. `recorded_commit_shas` is modeled as synchronous, but it is an asyncpg query — the plan's call site is not awaited (Task 2 / Task 4).**
Task 2 specifies the new store method as `recorded_commit_shas(repo: str) -> set[str]` and Task 4 step 4 calls it as `recorded = self._store.recorded_commit_shas(repo)` — with no `await` and a plain `set[str]` return type. But `PgEpisodicStore` runs on an asyncpg pool (`async with self._pool.acquire() as conn: ... await conn.fetch(...)`), and every sibling method (`append`, `query`) is `async def`. The plan is internally asymmetric here: it correctly awaits `self._store.append(...)` and `self._embedder.embed(...)` a few lines away, but leaves this one un-awaited.

Failure scenario, if implemented literally as written: the method can't be synchronous (a bare `conn.fetch` needs a running loop), so it becomes `async def` and returns a coroutine; the un-awaited call site then evaluates `if after in recorded`, i.e. `after in <coroutine>`, which raises `TypeError: argument of type 'coroutine' is not iterable` on the first step — the idempotency check (the spec's central guard and Verification item 3) never runs.

Fix: specify the method as `async def recorded_commit_shas(self, repo: str) -> set[str]` on both the ABC and `PgEpisodicStore`, and await it at the call site: `recorded = await self._store.recorded_commit_shas(repo)`. Everything else about the idempotency design (union of all stored `commit_shas`, precise over a time-watermark, resumable, safe against interleaving live 4.3 writes) is correct and needs no change.

### Positive Notes
- **The two load-bearing git assumptions are empirically correct.** I ran them against this repo's real history: `git log 4b825dc…4904..<root>` lists the root commit and the `--numstat --shortstat --end-of-options` form the collector uses succeeds over that empty-tree range (exit 0); `git rev-list --reverse --first-parent --parents --end-of-options HEAD` emits the root line with **no** parent field (so `before` correctly falls back to the empty-tree constant) and subsequent lines as `<commit> <first-parent>`. The uniform "every commit is one `resolve(before, after)` call, root included" design holds.
- **Bare-store reuse of `resolve` is valid.** `resolve` reads the roadmap via `git -C <repo> show <ref>:<path>` and commits via `git log <before>..<after>` — both object-store operations that work against the `--mirror` bare clone; `_current_branch`'s `rev-parse --abbrev-ref HEAD` also resolves on a bare mirror. No worktree needed, satisfying the spec's worktree-churn guard.
- **Idempotency reasoning is precise and correct.** `after` is always the newest commit in `before..after`, so it always lands in its own entry's `commit_shas`; the SHA-set (built from `unnest(commit_shas)` across all entries) therefore covers both prior backfill runs and live pushes, and a merge step's `git log P1..M` aggregating side-branch commits doesn't create gaps or duplicates. The local `recorded` update makes intra-run duplicate `after` values safe, and per-entry `INSERT` commits make an interrupted run resumable.
- **Error-contract deviation is deliberate and justified.** Task 1 correctly refuses to copy the siblings' `check=True` and instead returns `[]` on non-zero, so an empty/unborn-`HEAD` repo yields no steps instead of raising — a real DEVIATION from the sibling convention, reasoned out rather than blind.
- **Field/type/wiring fidelity is exact.** `EpisodicEntry` construction, `content = "\n".join([*completed_tasks, *messages])`, `changed_at = commit_timestamp(bare, after)`, the empty-content embed guard (defensive, documented as never-firing), and the Task 5 composition-root wiring all mirror `EpisodicWriter`/`main.py`/`scripts/backfill.py` faithfully; all referenced settings (`postgres_dsn`, `ollama_url`, `embed_model`, `ollama_api_key`, `canonical_refs`, `mirror_root`, `github_org_logins`, `github_app_*`) and the `src/episodic/schema.sql` path exist.
