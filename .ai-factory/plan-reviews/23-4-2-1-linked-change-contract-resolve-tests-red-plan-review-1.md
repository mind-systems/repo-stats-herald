### Critical Issues

**1. The done-marker identity key is left unspecified, and the "reworded" variant in the relocated-line test risks pinning an ungreenable red test.**
This task exists to *pin* the semantics that 4.2.2 must satisfy, so the identity key of a done-marker is the crux — and the plan leaves it ambiguous. Spec 11 keys markers by "task text/**identifier**" (either/or), and the plan echoes that without deciding. The consequence surfaces in Task 3's relocated-already-done case, which lists the adversarial mutation as "moved/reindented/**reworded**":
- If 4.2.2 keys the done set by **full line text** (the natural reading of set-difference over `[x]` lines), then a **reworded** already-`[x]` line has a *different* key in `after` than in `before`. It appears in the `after` set only → it lands in `completed_tasks` → **false positive**. The red test asserting it does NOT appear would then be **impossible to green** with spec 11's specified algorithm, and the milestone loops.
- The ROADMAP contract line (line 50) and spec 11's verification both scope the trap to **moved / re-indented / reformatted** lines — not reworded ones. The plan's own concrete parenthetical also narrows the planting to "changes position/indentation." The word "reworded" in the Task 3 prose is the outlier that an implementer could take literally.

Fix before implementing — pick one and state it explicitly in Task 1's contract docstring and Task 3:
   - **(preferred)** Pin the done-marker identity to the **stable task identifier** — the leading `N.N.N` token present on every roadmap line (e.g. `**4.2.1 —**`). Then move, re-indent, *and* reword of the description all preserve identity, giving the strongest possible adversarial test that 4.2.2 can still green. Ensure the conftest fixture writes roadmap task lines that carry such identifiers.
   - **(fallback)** Drop "reworded" and restrict the adversarial planting to position/indentation only (matching the ROADMAP line and the plan's own parenthetical), keying by whitespace-normalized line text.

   Either way, the ambiguity is a fantasy hole precisely where the task's whole value lies; it must be closed here, not discovered in 4.2.2.
